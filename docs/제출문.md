# 인증 구현 설명서 (여섯 항목)

## ① 무엇으로 붙였나

- **직접 구현이 아니라 라이브러리를 썼습니다.** 서버 쪽 검증은 **`@simplewebauthn/server` v13.3.3** 하나만 씁니다.
- 브라우저 쪽은 **표준 WebAuthn API를 직접 호출**했습니다(`navigator.credentials.create` / `.get`). 클라이언트 라이브러리는 쓰지 않았습니다.
- 외부 **인증 서비스(Auth0·Firebase Auth·Clerk 등)는 쓰지 않았습니다.** 계정과 공개키는 제 서버 저장소에만 있습니다.
- 나머지 구성: Node.js 20+, Express 4, 저장소는 Upstash Redis(Vercel KV), 배포는 Vercel.

## ② 왜 그걸 골랐나

- **비밀번호를 없애는 것이 이번 과제의 목적**이므로, 비밀번호를 대신 관리해 주는 인증 서비스는 오히려 배울 것을 가려 버립니다. 질문(challenge)을 만들고 보관하고 버리는 일을 제 코드 안에 두려고 서비스를 쓰지 않았습니다.
- 그렇다고 서명 검증까지 직접 짜는 것은 위험합니다. CBOR 해석, COSE 공개키 변환, 서명 검증은 한 줄만 틀려도 "항상 통과"가 되어 버리는 자리입니다. 그래서 **검증만 검증된 라이브러리에 맡기고**, 질문 발급·보관·폐기·세션·권한 판단은 직접 짰습니다.
- `@simplewebauthn/server`를 고른 이유: WebAuthn 표준만 구현한 작은 라이브러리이고, 계정·세션 구조를 강제하지 않아서 제 저장소 구조를 그대로 쓸 수 있었습니다.
- 저장소로 Redis(KV)를 고른 이유: Vercel의 서버리스는 요청마다 다른 인스턴스에서 돌 수 있어서, 파일이나 메모리에 담아 두면 **질문과 공개키가 사라집니다.** 인스턴스 밖에 두어야 했습니다.

## ③ 어디를 어떻게 고쳤나 — 네 흐름이 지나는 자리

1번 과제의 소개 페이지(공개 내용)는 `public/index.html`의 `<section id="public-zone">`에 그대로 두고,
그 아래에 경계선과 비공개 영역을 새로 붙였습니다.

| 흐름 | 브라우저 | 서버 |
|---|---|---|
| **등록** | `public/app.js` → `registerPasskey()` | `src/app.js` → `POST /api/register/options` (127행) → `POST /api/register/verify` (174행) |
| **로그인** | `public/app.js` → `loginWithPasskey()` | `src/app.js` → `POST /api/login/options` (240행) → `POST /api/login/verify` (260행) |
| **로그아웃** | `public/app.js` → `#btn-logout` 처리 | `src/app.js` → `POST /api/logout` (334행) |
| **비공개 자료 조회** | `public/app.js` → `showUnlocked()` | `src/app.js` → `GET /api/private/notes` (357행) / `GET /api/private/notes/:userId` (373행) |

거절을 만들어 내는 자리(T08-C41):

- 로그인하지 않은 요청 거절(401) → `src/app.js`의 `requireSession()` (95행)
- 다른 계정 자료 요청 거절(403) → `src/app.js`의 `GET /api/private/notes/:userId` 안의 계정 비교 (374~382행)
- 이미 쓴 질문 거절(401) → `src/store.js`의 `takeChallenge()` (111행, 꺼내면서 바로 지움) + `src/app.js` 184~190행·266~272행의 `null` 검사

### 질문(challenge)을 다루는 방식

- 서버가 만들어 **`chal:<flowId>` 키로 서버 저장소에 보관**합니다. TTL 120초.
- 확인할 때 **꺼내면서 곧바로 지웁니다**(`takeChallenge`). 그래서 같은 질문은 두 번 통하지 않습니다.
- 브라우저에는 질문 값만 전달되고, 판정은 전부 서버에서 합니다.

### 서버에 저장되는 값

등록이 끝나면 서버에는 다음이 저장됩니다. **비밀번호가 아니라 공개키입니다.**

```json
{
  "id": "mFImfA7lSg0M0SUv_DRKwjzu3kasCZ7E0sUTawDBx08",
  "userId": "jang",
  "publicKey": "pQECAyYgASFYIPXYxnx2R4RmQf95eNaY87ErTVk9NGPIRWlZCRCw_oKKIlggAjUzT6n8O5sbg_2JZXWB4v9OeKVWnjNKHPHiJ3L1sHY",
  "counter": 0,
  "label": "노트북 크롬",
  "createdAt": "2026-09-08T00:38:28.659Z"
}
```

- `publicKey`는 COSE 형식 공개키를 base64url로 적은 값입니다. 이 값만으로는 서명을 만들 수 없습니다.
- **개인키는 서버로 오지 않습니다.** 등록 요청 본문에 들어 있는 것은
  `id / rawId / type / response.clientDataJSON / response.attestationObject`뿐입니다.
  (실제 요청 본문 전체는 `evidence/검사기록.md` 3장에 그대로 적어 두었습니다.)

### 로그인 뒤 사람을 알아보는 방법 (T08-C32)

- **토큰이 아니라 서버 세션**입니다. 로그인에 성공하면 32바이트 난수를 만들어 서버 저장소(`sess:<sid>`, TTL 30분)에 담고, 브라우저에는 `httpOnly` 쿠키(`sid`)로만 내려보냅니다.
- 자바스크립트로 읽을 수 없고, 로그아웃하면 **서버 쪽 세션을 지우기 때문에** 같은 쿠키를 다시 보내도 통하지 않습니다.
- 기록에 남긴 세션 값은 앞 네 글자만 남기고 가렸습니다.

## ④ 안 열리는 것을 확인한 기록

전체 기록은 **`evidence/검사기록.md`** 에 요청과 응답을 그대로 적어 두었습니다(자동 검사 32/32 통과).
아래는 네 가지 확인의 요약이고, 각각 **통과한 요청과 거절된 요청을 나란히** 두었습니다.

### (1) 로그인 없이 열기

| | 요청 | 응답 |
|---|---|---|
| 거절 | `GET /api/private/notes` (쿠키 없음) | `401 {"error":"unauthenticated"}` |
| 거절 | `GET /api/private/notes/jang` (쿠키 없음) | `401 {"error":"unauthenticated"}` |
| 통과 | `GET /api/private/notes` (패스키 로그인 뒤) | `200 {"servedUser":"jang","count":4,…}` |

화면에서만 감춘 것이 아니라, 서버가 아예 내려보내지 않습니다.

### (4) 패스키 삭제 뒤 로그인

| | 요청 | 응답 |
|---|---|---|
| — | 패스키 2개 등록 후 `GET /api/passkeys` | `200 {"count":2}` — 이름·등록일·공개키가 함께 |
| — | `DELETE /api/passkeys/<노트북>` | `200 {"remaining":1}` |
| 통과 | 남은 휴대폰 패스키로 로그인 | `200 {"verified":true}` |
| 거절 | 지운 노트북 패스키로 로그인 | `401 {"error":"unknown_credential"}` |
| 거절 | 마지막 하나를 그냥 삭제 시도 | `409 {"error":"last_passkey"}` — 한 번 더 확인 |

화면에도 "지우면 이 계정으로 다시 들어올 수 없습니다"라고 미리 알리고 한 번 더 확인받습니다.

## ⑤ AI와 나

> ▢ 아래는 초안입니다. 실제와 다른 부분은 본인 기준으로 고쳐 주세요.

- **AI에게 맡긴 일**: WebAuthn 등록·로그인 흐름의 뼈대 코드, `@simplewebauthn/server` 사용법, 소프트웨어 인증기를 만들어 요청·응답 기록을 자동으로 남기는 검사 스크립트 작성.
- **내가 직접 판단한 일**: 비밀번호 대신 무엇이 그 자리를 채우는지를 기준으로 **인증 서비스를 쓰지 않기로** 결정한 것, 비공개 영역에 넣을 항목과 그것을 전부 가상 데이터로 두기로 한 것, 거절을 401(누구인지 모름)과 403(누구인지는 알지만 권한 없음)으로 나눈 것, 마지막 패스키를 지울 때의 동작을 어떻게 할지 정한 것.
- **AI 말을 따르지 않은 일**: 처음 제안은 화면에서 비공개 영역을 `display:none`으로 감추고 내용은 페이지에 함께 내려보내는 방식이었습니다. 그렇게 하면 소스만 열어도 다 보이므로 쓰지 않고, **로그인 뒤 API로만 내려보내는 방식**으로 바꿨습니다. 또 요청·응답 기록 패널이 비공개 내용을 그대로 찍는 것도 발견해서, 건수만 남기고 내용은 기록하지 않도록 고쳤습니다.

## ⑥ 아직 못 막은 것

1. **패스키가 0개가 된 계정은 아무나 가져갈 수 있습니다.** 지금은 등록 화면에서 계정을 고르고 바로 패스키를 등록할 수 있습니다. 어떤 계정의 패스키를 전부 지우면, 그 계정 이름을 아는 사람이 새 패스키를 등록해 그 계정의 비공개 자료를 볼 수 있습니다. — 막으려면 최초 등록에 초대 코드나 관리자 승인이 필요합니다.
2. **패스키 삭제에 다시 확인(재인증)을 요구하지 않습니다.** 세션 쿠키만 있으면 삭제가 됩니다. 원래는 삭제 직전에 패스키로 한 번 더 서명을 받아야 안전합니다.
3. **질문 보관 시간 120초는 다소 깁니다.** 필요한 시간보다 길어서 그만큼 재사용을 시도할 여유가 생깁니다. 30초쯤으로 줄이는 편이 낫습니다.
4. **요청 횟수 제한이 없습니다.** `/api/login/options`를 계속 부르면 저장소에 질문이 쌓입니다. TTL로 사라지긴 하지만 제한을 두지 않았습니다.
5. **서명 카운터(counter)를 저장만 하고, 값이 거꾸로 갈 때 막지는 않습니다.** 패스키 복제를 알아채는 신호를 흘리고 있습니다.

# 짧은 확인 방법 (4줄)

1. **어디로 가나요** — ▢ `https://______.vercel.app/` (새 시크릿 창에서 그대로 열립니다)
2. **세 단계 안에 무엇을 하나요** — ① 첫 화면에서 공개 소개 내용을 확인합니다 ② 아래로 내려 점선 경계선 아래 "나만 보는 자리"가 자물쇠로 잠겨 있는지 봅니다 ③ 개발자 도구(F12) → Network에서 `GET /api/private/notes`를 직접 열어 봅니다.
3. **무엇이 보이면 통과인가요** — 공개 영역은 그대로 보이고, 비공개 영역에는 자물쇠와 안내만 보입니다. 페이지 소스와 API 응답 어디에도 비공개 내용이 없고, `/api/private/notes` 요청은 **401**로 거절됩니다. 비밀번호 입력칸은 어디에도 없습니다.
4. **안 될 때는 무엇이 보이나요** — 첫 접속이 느리면 새로고침(F5) 한 번 해 주세요. 패스키 창이 뜨지 않으면 주소가 https인지, 브라우저가 패스키를 지원하는지 확인하면 됩니다. 심사에는 패스키 등록이 필요 없습니다. 잠긴 자리는 열지 않으셔도 됩니다.

# AI와 내 판단 (3줄)

- **AI에게 맡긴 일**: WebAuthn 등록·로그인 흐름의 뼈대 코드와 검사 스크립트 작성.
- **내가 직접 판단한 일**: 인증 서비스를 쓰지 않기로 한 결정, 비공개 항목 선정과 전부 가상 데이터로 두기, 401과 403의 구분, 마지막 패스키 삭제 시 동작.
